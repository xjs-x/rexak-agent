- 当前命令默认无交互 stdin，没有 PTY、按键发送、终端屏幕或持久 shell 会话。

- 进程模块记录输出尺寸及超限标志，但仍需实现真正的存储配额和超限处理。

## 4. 核心设计

### 4.1 唯一执行内核，统一数据归属

调用路径：官方 `create_agent` → Rexak 工具适配 → Executor API → 进程/PTY 管理 → 程序。

- LangGraph checkpoint：计划、对话与工具引用。
- 控制端业务表：操作请求、证据关联、值班委托及执行状态投影；值班委托只有此处一个可写真源。
- Executor 台账：真实进程、终端会话、输入操作回执及执行事件。
- artifact：命令/脚本快照、原始输出、终端快照和结果文件。

PTY 和普通命令共用操作身份、环境构建、输出存储、取消、错误分类及能力预检。PTY 增加终端所需机制，不再建立另一套任务平台。

控制端协议定义置于 `contracts/`，前端从 OpenAPI 生成。Executor 独立包通过可复现的协议生成或同步校验消费执行协议，不导入控制端仓储，不手工维护另一套枚举。

### 4.2 三类身份分开

- `session_id`：Rexak 对话和工作区。
- `terminal_id`：该对话中的某个长期终端。
- `operation_id`：一次打开、发送、调整、关闭或执行操作；普通进程另有 `job_id`。

原生 ARTEX 用 `session_id` 指终端，迁入后使用 `terminal_id`，避免与 Rexak 对话 ID 混淆。

打开终端和每次发送输入都先持久化操作身份，再派发。重试同一操作返回已有回执；不同参数使用同一 ID 则冲突。终端输入串行处理，携带序号和当前控制版本，拒绝旧方向继续写入。

进程启动或 PTY 写入与数据库之间无法形成跨系统原子事务。若在“可能已执行、回执未落库”窗口崩溃，标记 `unknown`，禁止自动再次启动或再次发送；不能承诺任意故障下严格恰好执行一次。

### 4.3 工作区、会话与恢复

- 文件工具、命令、脚本及终端默认共享同一 session 工作区。
- 默认使用独立的 `run_command`；需要连续输入或保留 `cd`、变量及程序上下文时，按需打开持久终端。独立命令不隐式继承上一条命令的目录或环境变更。
- 同一对话跨 run 可继续访问其终端；其他对话不可访问。权限检查落在执行端，控制端检查只是提前反馈。
- API、Runner 或 SSH 连接重建不主动销毁执行端会话。
- 非交互式长任务：要求 Executor 重启时进程继续运行、日志在采集配额内持续落盘，服务恢复后可以重新查询、读取和取消。使用独立会话、挂断信号处理、日志重定向和独立任务包装进程实现；部署停止流程不得连带回收这些任务。执行超时及输出边界也需在 Executor 离线期间继续有效，不能只依赖其内存定时器。
- 非交互任务保存进程身份及持久完成回执。Executor 离线期间结束的任务，通过回执取得退出码；缺少回执时标记未知，不能用“PID 不存在”推断成功。包装进程不持有可供模型复用的管理令牌或控制端凭据。
- 交互式会话：采用已确认的 A 方案。Executor 重启后保留日志和台账，核对残留进程；丢失 PTY 句柄则明确标为不可继续交互或状态未知，不自动新建相同程序或重发输入。
- 本轮不引入独立终端守护服务，不承诺 Executor 重启后无缝重新接管原 PTY。非交互任务的独立包装进程与这种 PTY 接管服务是不同机制。Kali 整机重启后的原进程存活不在保证范围内。

### 4.4 等待结束、操作完成、进程退出分别表达

一次 `shell_send` 返回，不代表终端进程退出。输出静默、出现提示符、等待超时只表示本次等待结束，不能直接生成任务成功结论。

返回至少区分：

- `operation_status`：本次调用是否受理、完成或失败。
- `process_state`：程序是否仍在运行、已退出或未知。
- `wait_reason`：输出可读、提示符、静默、进程退出、等待超时、用户中断。
- `exit_code`：仅在取得真实退出码时提供。

一次性命令的交互等待阈值与执行硬超时分开。交互等待默认值暂取 10 秒、允许配置；等待到期自动返回已有输出和同一 job，不重新提交或重新启动进程。真正执行超时才触发终止。长期任务允许不设执行截止时间，不继承普通命令的默认 120 秒硬超时，保留单次调用、取消、存储及资源边界，不新增任务总时长或费用上限。

### 4.5 调整唤醒机制

把“当前动作依赖的 job”与“作为会话资源长期存在的终端/监视器”分开。

- 长期资源仍运行，不阻止 Agent 处理其他工作或完成当前阶段。
- 等待对象明确为具体 job、输出位置或 watch 事件；按所等待的条件唤醒。等待多个任务时默认任一相关结果满足条件即可继续；只有明确需要汇总时才等待全部。
- 监视命中、退出和失败形成可补读事件，记录消费位置并去重，避免重复模型调用。
- Agent 活跃时，在一致边界注入相关通知；明确等待该事件且当前委托仍有效时重新排队。阶段已结束且没有持续处理委托时不自动发起模型调用，见 4.10。
- 用户暂停时只记录事件，不擅自恢复模型推进。终止通过明确的取消/关闭操作完成。
- 终端输出按工具数据处理，不作为用户新指令，不触发目标授权扩展。

### 4.6 输出和资源控制

- 普通命令分别保存 stdout/stderr；PTY 输出是合流，不虚构两个独立流。
- PTY 原始输出在采集配额内持续落盘，内存环形缓冲只作加速，不能成为唯一历史；达到配额后的处理见 4.9，不声称超额部分仍有完整原件。
- 显式 cursor 可重读，读取到当前末尾不等于进程退出；不使用多个消费者共享的隐式破坏性游标。
- 长输出分页并落 artifact，模型只收到有界内容；UTF-8 跨块解码正确，未知编码保留原字节并显式报错。
- 屏幕快照是原始输出的派生视图，保留关联字节位置、尺寸和采集时间。
- 对单进程输出、终端数量和磁盘使用设置可配置限制；触发时记录实际原因和保留区间。
- 监视进程采用明确的日志保留策略，不能沿用 ARTEX 临时目录自动删除来处理正式证据。
- 取消依次执行正常终止和强制终止，并核对结果；无法确认退出时显示未知。

### 4.7 阶段结束后保留资源（已确认）

阶段结束后默认保留终端、监视器及仍需使用的后台资源，供同一对话续聊；不会因为模型回复结束、输出静默或固定空闲时间而自动关闭资源。

保留必须同时满足三项条件：

| 条件 | 具体要求 |
|---|---|
| 可见 | 阶段报告和 UI 展示保留资源的 ID、类型、用途、实际状态及最近状态核对时间；无法核实的状态明确标为未知 |
| 可终止 | Agent 能显式关闭单个资源，用户能终止相关任务；取消结果必须区分请求已发出与进程已确认退出 |
| 有配额 | 磁盘、输出量及并发数量有可配置上限，防止长期对话无限积累；日志超限默认保活，具体规则见 4.9 |

时间仅用于提示：在阶段报告中说明哪些资源长时间没有输出，供 Agent 或用户判断是否继续保留。最近输出、最近输入和实际进程状态分别记录；没有输出不等于进程无用或已经退出。提示本身不触发关闭，不为重复提示额外循环调用模型。

报告分别列出“本阶段结果”“待完成工作”“保留资源”。例如：`保留资源：2 个交互终端、1 个监视器`。不能把这些可继续使用的资源统称为“3 个任务未完成”，也不能用“本阶段已完成”暗示所有进程已经停止。确实尚未取得结果的工作仍列入待完成工作，不能改名为资源后掩盖未完成状态。

本节禁止因阶段结束或空闲时间自动清理。采集日志超限时默认不主动终止进程，只有显式选择超限终止策略才终止相关进程；程序自身写文件遇到磁盘不足的行为不在保活保证内，见 4.9。

### 4.8 工具环境分层

用户认可分层原则。当前草案采用以下默认分工，系统级安装和升级的具体权限不据此扩大：

- 基础 shell、解释器及检索程序在部署时准备并验证。
- Kali 已安装程序可以直接调用，以实际路径、版本和能力清单呈现，不为每个程序新增同义工具封装。
- 任务依赖在对话工作区的虚拟环境或本地依赖目录内安装和复用，避免修改其他任务的依赖。
- 系统级软件通过环境维护流程管理。
- 安装后检查实际可用性并刷新清单；失败给出具体原因，不把安装尝试记录为能力已具备。

### 4.9 输出超限默认保活（已确认）

执行方式与超限策略是独立维度。普通进程、前后台、PTY、是否一次性命令，都不能用来推断资源是否可以终止。普通后台进程也可能承担持续可用的能力，一次性计算也可能难以重做。

- 默认保活：采集输出达到额度后，停止持久保存超额部分，继续有界读取并排空输出，避免管道堵塞。明确记录日志缺失的起始位置及能够核实的缺失区间；无法准确计数时如实标注，不能虚构连续日志。
- 超限终止必须显式选择：策略绑定具体资源并持久化。不得根据程序名称、任务类型或是否后台自动选择终止。
- 配额告警提供给 Agent 和用户；Agent 可以结合当前用途显式关闭资源，系统不从静默或执行方式推断其无用。
- 已保存的证据不因日志超限自动删除。日志截断与真实执行状态分别表达，不把截断直接写成执行失败，也不把有限日志标为完整证据。
- 采集日志额度与程序自行写文件的磁盘额度分开。程序自行重定向或创建文件可能绕过 stdout/stderr 采集器；工作区存储需独立监测和限制。
- “保活”只保证不因采集日志超限主动终止进程，不能保证程序在自身写入失败、磁盘耗尽或系统资源不足时仍正常运行。相关故障保留真实状态与错误。
- 采集和超限策略需在 Executor 重启期间持续执行；非交互任务不能仅直接重定向到无上限文件后依赖 Executor 在线巡检。

### 4.10 值班委托与资源存活分离（已确认）

值班状态是独立维度：资源存活不代表 Agent 仍被委托处理该资源的事件。阶段结束后，保留资源默认处于“存活但未委托”；只有明确承担持续处理任务时，相关事件才自动唤醒 Agent。

| 场景 | 事件处理 |
|---|---|
| Agent 正在执行相关工作 | 事件持久记录，在一致边界注入通知 |
| Agent 明确等待指定事件，或存在有效的持续处理委托 | 匹配条件时去重并唤醒，继续经过原有 Runner 和官方 Agent 循环 |
| 阶段已结束，仅保留资源供续聊 | 记录事件、更新 UI，不自动发起模型调用；下次对话聚合注入 |
| 用户暂停 Agent | 继续记录和展示事件，暂停优先于值班委托，不自动恢复推进 |
| 用户取消值班委托 | 停止该委托的自动唤醒，资源保留；事件继续记录和展示 |

委托至少明确关联资源、关心的事件条件及待处理目标，不能把任意输出都当成重新工作的理由。委托是控制端领域记录；Executor 只负责实际资源、观察及执行事件，不自行决定是否调用模型。UI 分别显示资源状态、值班状态与 Agent 运行状态。

“取消委托”和“关闭资源”是两个独立操作。取消委托不发送终止信号，可以重新委托；关闭进程则不能承诺恢复原会话。取消时使该委托的排队唤醒和后续派发失效，不影响同一对话其他有效工作；已经发生的副作用不能撤回，已提交进程不会被隐式杀死。重新委托需要明确动作，普通续聊不会自动恢复已经取消的委托。

不唤醒不等于丢弃。未委托或暂停期间的事件照常持久记录、展示；下次对话按资源、事件种类与时间范围形成有界聚合摘要，附事件引用、重要状态变化和可读取详情，不能把全部输出塞入上下文。摘要只作为工具事件数据，不作为新的用户授权，也不自动重放历史操作。

事件记录、UI 已读和模型已获知分别处理。持久事件 ID/序号用于去重和补读，只有摘要及其覆盖范围实际持久进入对话后才推进相应交付位置；生成失败或 Runner 中断时可重新核对。聚合不删除原事件，重启后不依赖内存清空式通知队列。

采集日志截断与事件持久化分开记录：若事件关联的输出原件已因额度缺失，事件详情必须显示证据可用性，不能把事件摘要当成完整输出。任意磁盘故障下不承诺记录绝对不丢失；发生无法落盘或无法核实的缺口时必须显式暴露，不虚构连续历史。

## 5. 已确定的可信执行策略

本次将新增明确的部署配置/能力状态，使指定 Kali 可以执行命令和交互程序。该配置由部署端管理，模型不能自行开启或扩大执行策略。

- 不逐条人工审批普通命令。
- 保留实际操作记录、操作幂等、取消、工作区归属与控制版本检查。
- 子进程使用筛选后的环境；不继承 Executor 管理令牌、模型 Key 或控制端数据库凭据。
- 默认 cwd 属于当前工作区，但 cwd 和文件工具路径检查不等于进程沙箱，不声称它们限制了任意命令的文件系统访问。
- 现有 HTTP/浏览器目标校验继续生效；通用程序在可信模式下没有逐目标的强制网络隔离。
- 能力报告明确区分 `execution_mode=trusted` 与 `network_isolation=unavailable`，允许二者同时成立。
- 没有配置可信执行、或部署能力不满足时，返回具体不可用原因，不伪装可用。

该决定需要新增正式 decision，更新旧命令关闭策略、相关测试和 UI 文案；不能仅把旧代码的 `False` 改为 `True`。

## 6. ARTEX 中需要适配而非照搬的部分

1. PTY 的 256 KiB 内存缓冲不能代替持久化证据。
2. `dispatchWaiter` 将静默、超时等结果装成 completed 通知；迁入后必须保留真实等待原因。
3. 输入发送没有 Rexak 的持久操作去重，需要补齐崩溃窗口与未知状态。
4. `withEnv` 继承进程环境；迁入后必须保留 Rexak 的环境边界。
5. `Manager` 的内存任务、临时目录及清理方式不能代替 Executor 台账和 artifact 生命周期。
6. `server/customtool.go` 的脚本另走 `execPython`；迁入后统一进入命令执行内核，保留脚本内容和参数版本。
7. ARTEX 的暂停/会话关闭行为不能覆盖 Rexak 已决定的“暂停推进，保留远端真实状态”。

来源记录也需一并处理：ARTEX 根目录包含 AGPL-3.0 `LICENSE`；本地 `norma/` 未发现独立的 `LICENSE`，其来源说明见根 `go.mod`。实施前记录实际复用文件与依赖的许可和来源，不能直接假定所有文件同一授权；改用 Python 本身不等于完成来源核对。

## 9. 讨论收敛点

已收敛的决定不再重复询问：

1. 完整能力迁入现有 Python 架构；保持官方 `create_agent`。
2. 指定 Kali 可信执行，不逐条审批普通命令；如实标明网络隔离能力。
3. A 方案按任务类型细化：非交互长任务要求进程和日志跨 Executor 重启存活；交互式 PTY 允许中断，不引入独立终端守护服务。
4. 默认独立命令，按需持久终端；共享对话工作区。
5. 短等待到期自动返回同一后台 job；执行超时单独控制，长期任务可以不设执行截止时间。
6. 按具体任务或事件等待，任一相关结果可继续；长期资源不阻塞推进，暂停时不自动恢复。
7. 工具环境采用分层原则；当前草案的任务依赖与系统环境分工见 4.8。
8. 阶段结束后保留资源供续聊，必须可见、可终止、有配额；长时间无输出只提示；报告区分保留资源与待完成工作。
9. 采集日志超限默认保活，只有显式指定才终止；该策略独立于执行方式。自行写文件的磁盘额度另行处理，不承诺存储耗尽后程序仍正常工作。
10. 值班委托独立于资源存活；阶段结束默认存活但未委托。取消委托不关闭资源，未唤醒事件继续记录展示，并在下次对话以聚合摘要注入。

整版方案已由用户确认。独立编码规格将讨论决定展开为协议、模块、默认值、生命周期、测试及提交要求；编码者依据行为规格与本仓库代码实现，无需阅读或复制外部项目。实际新增依赖的许可、兼容性和部署能力仍须核对。

编码者按 M0–M5 完整实现并自测，只做一次最终提交；本会话智能体负责独立复核及两端部署验收。本轮只更新交接文档，没有执行命令能力迁移，没有进行真实目标或真实模型效果实验，不能把任何新增能力标记为完成或已部署。
