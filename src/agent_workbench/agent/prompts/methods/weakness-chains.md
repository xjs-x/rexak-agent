# 弱点关系驱动的持续探索

按需加载的方法资料。它说明**怎么把已有弱点变成后续路线**，不重复系统提示里的硬性约束。

## 1. 先区分三类弱点

| 类型 | `weakness_kind` | 含义 | 典型处理 |
|---|---|---|---|
| 独立缺陷 | `vulnerability` | 本身可成立的缺陷 | 走验证：确定性核验后由系统写 confirmed |
| 使能条件 | `enabling_condition` | 单独看未必是缺陷，但降低了后续利用的门槛（多余信息、宽松校验、可预测标识、会话未收敛等） | 记录条件，寻找能消费它的路线 |
| 未判定 | `unclassified` | 还没判断 | 先补齐适用条件，再归类 |

把它当成"严重等级"来用是错的。一个 `enabling_condition` 可能比若干低影响独立缺陷更有价值。

## 2. 记录一个弱点时要写清四件事

1. **是什么**：`title` + `description`，只描述观察到的现象与判断，不写"可能能 getshell"这种结论。
2. **适用到哪**：`applicability_json` —— 适用资产、身份、已知前置条件、限制。
   复用已有 `asset_id` / `identity_id`，不要新建身份。
3. **它提供了什么条件**：`provided_conditions_json` —— 每条条件一个稳定 `key` 与一句 `statement`，
   并给出 `evidence_refs`（依据引用）。**引用说明判断依据，不证明条件已成立。**
4. **它通向哪里**：`connection_review_json` —— 已产生的后续线索 ID，或一句"暂未找到后续用途"的说明。
   两者都没有的判断不算完成。

## 3. 建立关系，而不是重复叙述

`record_lead` 里的关系参数：

- `source_weaknesses_json`（`basis`）：这条线索**从哪个弱点/条件**获得依据。
  带 `condition_key` 时，引用的是那个弱点里的一条具体条件。
- `result_weaknesses_json`（`result`）：这条线索的验证**实际产生或更新**了哪个弱点。
- `required_conditions_json`：还缺什么。可以指向已有弱点条件、身份/资产，
  或另一条线索预期产出的结果（`producer_lead_id`，只表示依赖意图）。
- `actionability_json`：当前能否推进。
  - `ready`：有明确下一步，且前置条件已满足；
  - `needs_condition`：缺条件，要写清缺什么；
  - `no_new_action`：确实没有能区分现有未知的新动作。必须写 `unknowns`，
    并说明为什么现有尝试或证据已经足够，不能只写"没有新动作"；
  - `needs_review`：依据变化了，需要重评。

**两个弱点分别成立 ≠ 组合成立。** 组合本身就是一条待验证的假设：
用 `basis` 把它们挂在同一条线索上，让线索去验证组合，不要直接写成结论。

## 4. 计划怎么承接

- `kind="coverage"`：还有覆盖缺口要补；
- `kind="followup"`：沿链条推进（消费某个条件、验证某个组合）；
- `kind="mixed"`：一次动作同时服务两者。
- `lead_ids`：一个步骤可以服务多条线索。条件相同、结论独立的线索共用步骤即可，不必合并。

计划步骤的条件和来源弱点**从线索与关系读取**，不要再维护一份 depends_on 清单。

## 5. 什么时候算"这条路线暂时走不通"

按顺序检查，不要跳步：

1. 做一次能区分"条件问题"与"路径不通"的最小验证；
2. 条件不成立 → `needs_condition`，写清缺什么；
3. 假设被反证 → 用 `record_lead` 更新状态并说明**排除条件**；
4. 有可推进方向 → 继续，不要用"不是当前目标必需"当豁免；
5. 只有全部有效方向都确实需要外部条件时，才进入等待用户。

## 6. 条件变化后的重评

出现下列变化时，回头看那些依赖旧条件的线索：

- 新弱点出现，或已有弱点的条件被修订；
- 身份 / 认证状态变化；
- 来源弱点被反证或适用范围收窄（此时**只标记待复核，不级联判定所有下游失败**）；
- 主线受阻 → 重新排序其他未完成路线。

重评要有依据：说明这次变化**真的**改善或恶化了哪个条件。没有变化就不要重复同一个尝试。
