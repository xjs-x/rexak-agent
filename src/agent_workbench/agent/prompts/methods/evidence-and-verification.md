# 从观察到发现：证据与验证

适用于：你已经拿到一个可疑观察，正在决定它算不算"发现"。

## 三段式

```
工具返回 -> 观察 -> 候选发现 -> 验证记录 -> confirmed / disproved / inconclusive
```

**每一步都不能跳。** 模型判断再合理，也只是一条候选。

## 什么样的证据能用

- 原始响应字节（工件），而不是你复述的摘要。
- 请求与响应成对：能说明"发什么、收什么"。
- 采集时间与身份归属：不同身份的响应不能混用。
- 可重复：换个时间/顺序再做一次仍然成立。

## 确认条件

按发现类型选择验证方法，优先**可重复观察或确定性检查**：

- 认证/授权边界：同一资源在身份 A 与身份 B 下的状态码与响应体差异，且差异稳定。
- 输入校验：同一参数在有效/无效取值下的确定性行为差异，且能排除服务端随机性。
- 配置问题：可被直接读取的配置面（如暴露的状态页、目录列表）内容本身构成证据。

**不能**用的"验证"：
- "第二个模型也同意" —— 那不是独立验证。
- "扫描器告警了" —— 那是线索来源，不是确认。
- "返回了 200" —— 200 只说明请求成功。

## 推翻也是有价值的结论

线索被 `disproved` 时必须记录**排除条件**：什么条件下不成立、测了哪些取值。
不要写成"不存在这个漏洞"。

## 失败与不确定

- 工具故障（超时、连接被拒、编码无法解析）→ 记录为**受阻**，不是阴性。
- 无法判断 → `inconclusive`，在报告中说明缺什么。
- 需要人工（验证码、MFA）→ `waiting_user` 并说明缺什么。
